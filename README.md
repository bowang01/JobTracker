# JobTrack

A multi-user job application tracker. Java 21 + Spring Boot 3.5 + Thymeleaf (server-rendered, no separate front end) + Spring Security + Spring Data JPA + Flyway + MySQL 8.

## Getting started

### 1. Prepare MySQL 8

**Option A: an existing MySQL server.** Create a database and user (adjust the password):

```sql
CREATE DATABASE jobtrack CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'jobtrack'@'localhost' IDENTIFIED BY 'jobtrack';
GRANT ALL PRIVILEGES ON jobtrack.* TO 'jobtrack'@'localhost';
FLUSH PRIVILEGES;
```

**Option B: Docker.** `docker compose up -d` starts MySQL 8.4 on port 3306 with database, user and password all set to `jobtrack`.

Tables are created by Flyway on the first start (`V1__init.sql`, then `V2__question_language.sql`). You never run the schema by hand.

**Upgrading from a build with numeric ids:** ids are now UUIDs and the old migrations were merged into a fresh V1, so an existing database cannot be migrated in place. Stop the app, run `DROP DATABASE jobtrack;` (it is recreated on the next start), and empty `data/files` (uploads that belonged to the old rows). The initial admin is created again from the config on start.

### 2. Build and run

```bash
# Needs JDK 21 and Maven 3.9+
mvn verify                 # compile and run all integration tests (no MySQL needed, see "Tests")
mvn spring-boot:run        # start, then open http://localhost:5566
```

Users sign in with their **email**. On first start there is no administrator, so one is created with the email `admin@jobtrack.local` (`JOBTRACK_ADMIN_EMAIL`):

* if the `JOBTRACK_ADMIN_PASSWORD` environment variable is set, that becomes the password;
* otherwise a random password is generated and **printed once in the startup log** (search for "Created initial admin").

The admin settings are only read while the database has no administrator. To change the admin password later, use the Profile page.

Packaged:

```bash
mvn package -DskipTests
JOBTRACK_ADMIN_PASSWORD='use-a-strong-password' java -jar target/jobtrack-0.1.0-SNAPSHOT.jar
```

On Windows PowerShell, set variables with `$env:JOBTRACK_ADMIN_PASSWORD='...'`, or put them in the IntelliJ run configuration.

### Configuration

| Environment variable | Default | Purpose |
|---|---|---|
| `JOBTRACK_DB_URL` | `jdbc:mysql://localhost:3306/jobtrack?createDatabaseIfNotExist=true&...` | JDBC URL |
| `JOBTRACK_DB_USER` | `jobtrack` | Database user |
| `JOBTRACK_DB_PASSWORD` | `jobtrack` | Database password |
| `JOBTRACK_DATA_DIR` | `./data` | Uploaded files are stored in `files/` under this directory. **Back it up together with the database.** |
| `JOBTRACK_ADMIN_EMAIL` | `admin@jobtrack.local` | Initial admin email |
| `JOBTRACK_ADMIN_PASSWORD` | empty (random) | Initial admin password |

Upload limits are in `application.properties`: 5MB per file (`jobtrack.upload.max-file-size`); PDF, DOC, DOCX and TXT are allowed.

> The schema needs MySQL 8.0.16 or later (CHECK constraints are enforced from 8.0.16).

> **Ids are random UUIDs** (generated by Hibernate, stored as `CHAR(36)`), never auto-increment numbers, so URLs like `/applications/3f2c…` reveal nothing about how many records exist. UUIDs carry no insertion order: lists always sort by a real column (dates, company, round number), and status history breaks ties on `recorded_at`.

> Times are stored as local date-times (`DATETIME`) in the server's time zone. If the server is not in New Zealand, start the JVM with `-Duser.timezone=Pacific/Auckland`.

## Features

| # | Module | Scope |
|---|---|---|
| 01 | Accounts | Register with just an email and password, sign in with email, sign out, edit profile and password |
| 02 | Applications | Create, view, edit, delete |
| 03 | Documents | JD text + JD file + CV + cover letter + other, with versions per type |
| 04 | Status & history | Manual status updates, backfilling, full timeline |
| 05 | Interviews | Round, time, type, duration, interviewer, location, outcome, reflection notes |
| 06 | Search & filter | Company, position, status, applied-date range; sortable; paginated |
| 07 | Dashboard | Totals, active, per-status counts, interviews in the next 14 days and the last 14 days, recently updated |
| 08 | Security | Data isolation, file permissions, CSRF, CSP, form and file validation, error pages |
| 09 | Interview questions | Personal question bank, separate from applications: technical and behavioral questions with your answer and a self-rating; technical questions can be tagged with a programming language (Java, C#, Python, ...); search and filter by type, language and rating |
| 10 | Interview hall | Questions users chose to make public, browsable by everyone, **including visitors who are not signed in** (questions only, never answers or authors); signed-in users can copy a question into their own bank |
| — | Admin | Monitoring overview (users, sign-ins, site-wide status distribution, storage, questions), all users' interview questions (no answers), user list with search, user detail, enable/disable, delete user (with all their data and files); read-only view of any user's applications |

### Roles

* **User**: tracks their own applications and keeps a personal interview question bank. Registration always creates a regular user.
* **Admin**: manages and monitors regular users. Admins have no dashboard or applications of their own and cannot change users' application data (enforced both by URL rules in `SecurityConfig` and by owner-only writes in `AccessGuard`). They can view users' applications and documents read-only, enable, disable or delete user accounts, see every user's interview questions, public and private, with their owner (but never answers or self-ratings), and remove inappropriate questions from the interview hall (this makes them private again; it never deletes them). There is no UI for promoting users; the initial admin is created from configuration.

## How the business rules are implemented

| Rule | Implementation |
|---|---|
| 1. Each application belongs to one user and cannot be transferred | `job_applications.user_id NOT NULL`; mapped `updatable = false`; the form object has no owner field (posting `ownerId` and similar is ignored, covered by a test) |
| 2. Current status and history stay in sync | Status changes only through `JobApplicationService.changeStatus`, which updates the application and inserts the history row in one `@Transactional` method; the edit form cannot change the status; creating an application also writes an initial history row |
| 3. Backfilling is allowed | `status_history.occurred_at` (when it happened) and `recorded_at` (when it was entered) are separate columns. Invariant: **the current status = the history entry with the latest occurrence time**. A normal update cannot be dated before the latest change; to record an earlier event, tick "Backfill history only" (the current status is unchanged) |
| 4. Unlimited interview rounds, unique numbers | No limit on rounds; `UNIQUE (application_id, round_number)` plus an application-level check for a friendly message |
| 5. JD text and JD file can coexist | `jd_text` column and `documents(doc_type = 'JD')` are independent |
| 6. Documents are versioned, never overwritten | Each upload gets `version_no + 1` and a random UUID filename on disk; a version is only removed when the user deletes it (with an extra warning when it is the only one) |
| 7. Deleting an application handles files | Rows are deleted in a transaction and the files on disk only **after the commit**; if an upload's transaction rolls back, the just-written file is removed, so there are no orphan files |
| 8. Status changes are manual | No automatic scraping of SEEK, Indeed or email |
| 9. Default status `SAVED` | New applications default to `SAVED`; entering "Applied" or later with no applied date fills it in from the event date. Creating an application as "Applied" with a past applied date dates the initial history entry to that day |

### Interview questions and the interview hall

* Questions belong to one user and are **private by default**. Admins can see all questions, including private ones and who owns them, in the interview hall and on the admin Questions page, but not answers or self-ratings. The owner can make a question **public**, which lists it in the interview hall for everyone. The hall is the only page visitors can open without signing in: they can browse, switch tabs, search and page through it, but saving a question or moderating needs an account (they are sent to the sign-in page).
* **Answers and self-ratings are always private.** The hall only exposes the question text, its type and when it was shared (through the `PublicQuestion` record, which has no answer field), never the author. Hall search does not look at answers either, so it cannot be used to discover them.
* Questions record no company or other source, so the hall never shows where a question was asked.
* Anyone can copy a public question into their own bank as a new private question without an answer.
* Making a question private again removes it from the hall immediately.

## Security

* **Data isolation**: every by-ID access to applications, interviews and documents goes through `AccessGuard`. Reads are allowed for the owner or an admin; writes for the owner only. Anyone else gets **404** (not 403), and ids are random UUIDs, so ids can be neither guessed nor probed. Interviews and documents are also checked to belong to the application in the URL.
* **Files**: stored outside the web root; only downloadable through the permission-checked `/documents/{id}/download`, always as `Content-Disposition: attachment`; extension whitelist plus file-signature (magic bytes) check, so a renamed `.exe` is rejected; the user's filename is only used for display.
* **Oversized files**: the 5MB business limit returns a clear message; the 20MB servlet limit is the backstop. The upload form also puts the CSRF token in the URL, so a body that cannot be parsed still shows a friendly message instead of a 403.
* **Accounts**: BCrypt passwords; registration only creates regular users; admins cannot disable, demote or delete themselves, and at least one active admin always remains; after an account is disabled or its role changes, that user's existing session ends on their next request.
* **Pages**: CSRF on by default; strict CSP (no inline scripts or styles); job links must be `http(s)://`, so `javascript:` links are rejected.

## Project layout

```
src/main/java/com/jobtrack
├── config/              security config, configuration properties, initial admin
├── domain/              entities and enums (User, JobApplication, StatusChange, Interview, ApplicationDocument, InterviewQuestion)
├── repository/          Spring Data JPA repository interfaces (implemented by Spring at runtime)
│   │                    + *RepositoryCustom interfaces for hand-written dynamic searches
│   └── impl/            *RepositoryCustomImpl: Criteria API implementations of the custom searches
├── security/            UserDetails, login success handler, account status filter
├── service/             service interfaces (+ their result records), AccessGuard (data isolation), shared helpers
│   └── impl/            *ServiceImpl: the @Service implementations (transactions live here)
└── web/                 controllers, form objects, global exception handling, flash helper
    └── state/           list-page filter/sort/page state kept in the session
src/main/resources
├── db/migration/        Flyway scripts (the only source of the schema)
├── templates/           Thymeleaf pages
└── static/              CSS / JS (no external dependencies)
```

* **Services** are interfaces in `service/`; controllers and other services depend only on the interfaces.
  The implementations in `service/impl/` are the Spring beans.
* **Repositories** stay Spring Data interfaces: simple queries are derived from method names or declared with
  `@Query`, and Spring generates the implementation. Searches whose conditions are optional
  (application list, question bank, interview hall, admin questions) are declared in `*RepositoryCustom` and
  implemented by hand in `repository/impl/*RepositoryCustomImpl` with the Criteria API; Spring Data merges them
  into the repository by naming convention.

## Mobile-friendly UI

* One shell for every page (`fragments/layout.html`): on phones and tablets a slim top bar plus a bottom tab bar
  (with a central "New" button) within thumb reach; from 1024px wide a fixed sidebar, with the content using the
  full width.
* Tables marked `rtable` turn into one card per row on phones (cells show their `data-label`); the application
  list gets sort chips there because the column headers are hidden.
* Search & filter panels fold away on phones (open on wide screens, tagged "Active" when a filter is set).
* 44px touch targets and 16px inputs on phones (so iOS does not zoom in), safe-area padding for notched phones.
* A web app manifest and icons: "Add to Home Screen" opens JobTrack full screen like an app.
* Sign-in and register pages: what JobTrack does on the left, the form on the right (form first on phones),
  with a link to the public interview hall.

## Clean URLs

Search, filter, sort, paging, tabs and messages never appear in the address bar:

* List pages (`/applications`, `/questions`, `/hall`, `/admin/users`, `/admin/questions`) are always opened at
  their plain URL. Filter forms, column headers, tabs and Previous/Next buttons POST to small endpoints such as
  `/applications/filter`, `/applications/sort` or `/hall/page`; the state is stored in the session
  (`web/state`) and the browser is redirected back to the plain URL (Post/Redirect/Get), so refresh and Back
  work without re-submitting forms. The state is per browser session and resets on sign-out.
* Messages (saved, signed out, wrong password, account changed) are flash attributes, so no `?error` or `?logout`.
* After a form on the application page, the page scrolls to the right section using a flash value
  instead of a `#fragment`.
* Detail pages keep their ID in the path (for example `/applications/3f2c9a1e-…`), so they can still be refreshed and bookmarked.

## Deployment (Hostinger VPS)

Pushing to `master` (or running the workflow by hand) runs `.github/workflows/deploy.yml`:

1. **test**: `mvn verify` (H2, no MySQL needed).
2. **build**: builds the `Dockerfile` and pushes `ghcr.io/bowang01/jobtracker:<commit sha>` and `:latest`.
3. **deploy**: sends `docker-compose.prod.yml` to Hostinger Docker Manager (project `jobtrack`), which pulls that exact image tag.

The app listens on port **5566**. On the VPS it is bound to `127.0.0.1:5566` only and also joins the shared `proxy`
Docker network as `jobtrack-app`, so a reverse proxy can reach it either way (example in `deploy/nginx.conf`).
MySQL has no published port.

### Demo account

For visitors (for example recruiters looking at the project), JobTrack can run a shared demo account:

* `JOBTRACK_DEMO_ENABLED=true` (on in `docker-compose.prod.yml`, off by default) creates a regular user
  `JOBTRACK_DEMO_EMAIL` / `JOBTRACK_DEMO_PASSWORD` on start, with fictional sample applications in every stage,
  status history, past and upcoming interviews and an interview question bank (most questions public, so the hall is not empty).
* Visitors who open `/` land on the interview hall, which starts with a short introduction and a **Try the demo**
  button (one click signs in to the demo account); the sign-in page has the same button.
* Because everyone shares it, the demo account cannot change its email or password and cannot share questions to the hall.
* Every night at 04:00 (NZ time) the demo user is deleted with all its data and files and created again
  (`JOBTRACK_DEMO_RESET_CRON`, Spring cron format; `-` turns it off). The reset needs an administrator to exist.

One-time setup:

* GitHub repository → Settings → Secrets and variables → Actions:
  * Secrets: `HOSTINGER_API_KEY`, `JOBTRACK_ADMIN_PASSWORD`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`
  * Variables: `HOSTINGER_VM_ID`, `JOBTRACK_ADMIN_EMAIL`
* After the first successful build, make the `jobtracker` package public (GitHub profile → Packages → jobtracker →
  Package settings), or run `docker login ghcr.io` once on the VPS with a token that has `read:packages`.
* The `proxy` network must exist on the VPS: `docker network create proxy`.
* Point the domain at the VPS, add the reverse proxy site (`deploy/nginx.conf`), then enable HTTPS.

Data lives in the Docker volumes `jobtrack_mysql` and `jobtrack_data` (uploaded files). Back up both together.

## Known trade-offs / next steps

* Status history is an append-only audit trail; single entries cannot be deleted in the UI (add another entry to correct a mistake).
* Files are stored on local disk; a multi-instance deployment needs shared storage (e.g. S3), which only means replacing `FileStorageService`.
* No password reset (needs an email service); admins cannot reset other users' passwords yet.
* The admin "User" filter lists every user; with many users it should become a search box.
